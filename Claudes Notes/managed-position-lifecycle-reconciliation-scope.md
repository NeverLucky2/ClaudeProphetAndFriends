## 3b. ROOT CAUSE — CONFIRMED (clean reads, 2026-05-29 after env recovered)

**Partial-fill PENDING hang (Symptom B) is fully root-caused. H1 + H2 CONFIRMED.**

Corrections to §3 written during the degraded window: entry fn is **`PlaceManagedPosition`** (not CreateManagedPosition); there is **no** `controllers/position_manager_controller.go`. All logic lives in `services/position_manager.go` (1493 lines).

**The bug:** `checkEntryOrder` (position_manager.go:504-538) is the ONLY transition out of PENDING and has a single branch:
```go
if order.Status == "filled" {        // line 511
    position.Status = "ACTIVE"; ... placeRiskOrders(...) ...
}
// no else → "partially_filled" (and every other status) does nothing
```
A partial fill (Alpaca `partially_filled`; Spark's 2-of-98 III) matches neither "filled" nor "0-filled", so the row stays PENDING forever. Cascade:
1. `checkPositions:468` routes PENDING back to checkEntryOrder + `continue` → **price never updates** ("frozen at $5.07") and **no bracket ever placed**.
2. `reconcileWithBroker:411-416` skips non-ACTIVE/PARTIAL → the 2 real broker shares are **invisible + unprotected** (entry-side sibling of the close-side orphan bug).
3. **No PENDING timeout** anywhere — only a 24h *display* filter in GetManagedPositions (hides, doesn't resolve).

Note: struct status `"PARTIAL"` exists but is used for partial **exits** only; entry path has no partial concept.

**Interface facts confirmed for the fix** (interfaces/interfaces.go:52-73):
- `Order.FilledQty float64` and `Order.FilledAvgPrice *float64` — partial fill data IS available from GetOrder.
- `TradingService.CancelOrder(ctx, orderID) error` exists (interfaces.go:48) — can cancel the unfilled remainder.
- Reuse mock `closeStubTrading` (position_manager_close_test.go) — has scripted GetOrder, `canceledOrders` tracking, `placedOrders` tracking. Exactly what the partial-fill test needs.
- Existing pattern to mirror: `flattenUnprotected` (FAILED + market exit) for the 0-fill-timeout terminal path; `placeRiskOrders` for bracket placement (already retries stop + auto-flattens on failure).

**Owner-approved fix (decided 2026-05-29): accept partial + cancel remainder.**
On `partially_filled` in checkEntryOrder: set `Quantity`/`RemainingQty = FilledQty`, `EntryPrice = *FilledAvgPrice`, status ACTIVE, **cancel the entry remainder** (CancelOrder) so it can't fill later and re-desync, then `placeRiskOrders` sized to the real filled qty. Plus a **PENDING timeout** (bounded passes/age) → terminal FAILED + flatten any stray fill, so a 0-fill or stuck order can never hang indefinitely.

**Delivery (decided): TDD on a branch, show diff before commit.** Branch fresh from main (current branch is `close-managed-position-fail-closed`, the close-side work — keep separate).

## 4. Root-cause hypotheses (H1/H2 now CONFIRMED above; H3/H4 still open)

**H1 (primary): the reconciler assumes fill-or-nothing and has no partial-fill path.**
A partial fill (2/98) is neither "0 filled → FAIL" nor "all filled → ACTIVE", so the record is stuck in PENDING indefinitely. Predicted code shape: the promotion check compares filled qty to ordered qty for equality, or only checks `order.Status == "filled"`, ignoring `"partially_filled"` and `filled_qty`.

**H2: PENDING positions never sync price/qty to broker truth.**
Record stayed frozen at $5.07 while broker showed $4.35 and 2 shares. The reconciler likely only updates `CurrentPrice`/qty for ACTIVE positions, so a stuck-PENDING record is invisible to monitoring (no stop protection on the 2 real shares — same danger class as the orphan bug).

**H3: HTTP 500 (Symptom A) is an unhandled error in `CreateManagedPosition`.**
Could be (a) Alpaca transient 500 surfaced raw, or (b) our code panicking/erroring on a specific broker response. The Go controller may be returning 500 instead of a structured error the agent can act on. Need to see the controller's error handling + whether SubmitOrder errors map to 500. NB: III on 5/26 had RVOL 1925× — possibly a halted/illiquid-name broker rejection mishandled as 500.

**H4 (unifying — owner's chosen frame): naive broker-vs-record reconciliation across the WHOLE lifecycle.**
- Entry side: partial fill → stuck PENDING (H1/H2).
- Exit side: known [`CloseManagedPosition` fail-open orphan bug](../memory/close-managed-position-fail-open-orphan.md) — marks CLOSED even when the exit order failed → unprotected orphan broker position (root cause of Coil UNH/ADI mismatch 2026-05-27).
- **Same weakness at both ends:** the manager trusts its own intent over broker truth and lacks a reconcile-to-broker step that handles the messy middle (partial, rejected, stuck). A single robust reconciliation routine (poll broker order/position truth; converge record state incl. partials; never leave unprotected real shares) likely fixes both ends.

## 6. Fix shape (TENTATIVE — do not implement until Phase 1 confirms)

A single broker-truth reconciliation routine that, per managed position each beat:
- Polls broker order + position truth.
- Handles `partially_filled`: either (a) accept the partial — set ACTIVE with `Quantity = filled_qty`, attach/resize brackets to the real qty, or (b) cancel remainder + flatten/keep per policy — but NEVER leave real shares unbracketed and NEVER stay PENDING past a bounded timeout.
- Adds a **PENDING timeout** → terminal state (FAILED + flatten any stray fill) so nothing hangs indefinitely.
- Mirrors the same truth-convergence on the close side (fixes the orphan bug): only mark CLOSED when broker confirms flat; otherwise CLOSING + retry/alert.
- Surfaces broker 5xx as a structured, retryable error (not a bare 500) so the agent can distinguish "retry" from "skip".

**Verification before "done"** (per feedback-verification memory): mock-based tests for the side-effecting reconcile/close funcs — test the executor, not just the predicate. Partial-fill, rejected-entry, Alpaca-5xx, and exit-order-fails cases all need explicit tests.

## 8. Pre-registered decisions — CONFIRMED 2026-05-31 (operator sign-off)

Part A is root-caused; these were the embedded choices "just execute" would have made by default. Pinned and operator-approved before coding (part of the Foundation sub-project of the uncorrelated-ballast pivot).

**D1 — Partial-fill race.** On `partially_filled` in `checkEntryOrder`: issue `CancelOrder` on the entry, **WAIT for the order to reach a terminal state, read the FINAL `FilledQty` from the terminal order, THEN `placeRiskOrders` sized to that final qty.** Never size brackets off a mid-flight read — eliminates the "N more fill during the cancel window → unbracketed sliver" race. Set `Quantity`/`RemainingQty` = final FilledQty, `EntryPrice` = `*FilledAvgPrice`, status ACTIVE.

**D2 — PENDING timeout.** 300s wall-clock (env `MANAGED_PENDING_TIMEOUT_SEC`, default 300). On expiry: PENDING → terminal FAILED + flatten any stray fill. Wall-clock (not pass-count) because heartbeat cadence varies 60s→daily across agents.

**D3 — Close-side retry exhaustion.** On exit-order failure: retry up to 3 times (next-beat backoff). If all fail → terminal **`CLOSE_FAILED`** (NOT CLOSED): does not free the segment lane, keeps existing stops in place if present, raises a hard operator alert, HALTs the agent. Never mark CLOSED without broker-confirmed flat.

**Boundary / measurement-window decisions (A↔B):**
- **Quarantine:** all closed records written before the A-fix landing date are NOT graduation-eligible (pre-fix data is poisoned).
- **Retroactive repair:** Fix 3's exit-reason derivation runs once over existing closed positions so historical records display honestly (cheap — tiny dataset). Fix 3 is the A/B boundary tool, not a peer state-machine fix.
- **Paper clock:** the ≥3-month graduation clock counts PAPER time; graduation requires clearing the 2× friction gate (friction is what makes paper-based graduation honest). Foundation delivers the machinery + starts the clock, NOT verdicts — nothing graduates for ≥1 quarter after A lands.
- **Options friction:** `apply-friction.mjs` does NOT model options (it skips them as "unrecognized asset class" — confirmed empirically 2026-05-31). Equity/ETF agents (Coil, Turtle) reuse the friction machinery as-is; instrument-aware options friction is a NAMED OPEN ITEM in B's spec, deferred to the defensive-Prophet build.
